# API Reference

This document tracks the Google APIs used by the server and their relevant capabilities and constraints.

Items marked **Verified (live, <date>)** were confirmed by calling the API on that date with a real DV360 account. Items marked **Verified (docs)** come from Google's documentation. Re-check versions and quotas before relying on them; Google changes both.

## Access summary

| | Bid Manager API v2 | Display & Video 360 API v4 |
|---|---|---|
| Cloud service | `doubleclickbidmanager.googleapis.com` | `displayvideo.googleapis.com` |
| Base URL | `https://doubleclickbidmanager.googleapis.com/v2/` | `https://displayvideo.googleapis.com/v4/` |
| OAuth scope | `https://www.googleapis.com/auth/doubleclickbidmanager` | `https://www.googleapis.com/auth/display-video` |
| Smoke-test call | `GET queries?pageSize=1` → `200` | `GET advertisers?partnerId=<partner>&pageSize=1` → `200` |
| Status | **Verified (live, 2026-11-05)** | **Verified (live, 2026-11-05)** |

- **Identity:** OAuth 2.0 user credentials of one DV360 user account (see "OAuth user credentials" in `decisions.md`). Both APIs must be enabled in the Cloud project, and one token carrying both scopes works for both.
- **Scopes are separate.** Neither scope grants the other API. **Verified (live).**
- **Quota project:** both calls returned `200` without an `x-goog-user-project` header (quota then falls back to the OAuth client's project). The server nevertheless sets the header explicitly from `GOOGLE_CLOUD_QUOTA_PROJECT` on every request (`integrations/google/auth.ts`). Using a quota project requires the caller to hold `serviceusage.services.use` on it. **Verified (live)** for the header-less case, and with the explicit header through the auth module (2026-11-05).
- **Scope breadth:** `display-video` also permits writes. The project's read-only boundary is enforced by code and review, not by the scope. **Verified (docs).**
- **Roles:** the calling account needs its own DV360 role on the partner or advertiser. Bid Manager report access is user-specific and cannot be delegated through query sharing. Google's docs say Read only is enough for reporting and for most DV360 `get`/`list` calls; **not yet verified live** with a Read only-only account.

## Bid Manager API v2

- **Purpose:** generate, execute, and retrieve performance reports.
- **Version:** v2 is the current version, with no announced sunset of the `queries` or `queries.reports` methods. Google has deprecated individual filters, metrics, and report types within v2 (e.g. `FULL_PATH` and `PATH_ATTRIBUTION` reports were sunset on 2024-05-01), so report fields must be checked against the current Filters and Metrics references in M3. **Verified (docs, 2026-11-04).**
- **`queries.list`:** returns the queries the calling account can see, including ones created in the DV360 UI; paginated with `nextPageToken`. **Verified (live).**
- **Quotas (Verified, docs, 2026-11-05):** 2,000 requests per project per day (can be increased) and 4 queries per second per project, shown in the Cloud console as 240 queries per minute per user. Daily quotas reset at midnight Pacific. `403 dailyLimitExceeded`: don't retry until the reset. `403 userRateLimitExceeded`: back off. Reporting quotas with **unpublished** limits also apply (ad-hoc report runs per day, concurrent reports, active scheduled reports) and surface as `429 RESOURCE_EXHAUSTED`.
- **Visibility (Verified, docs):** `queries.list` returns only queries *created by the calling user*, and other users' queries return `404`. Report access can't be shared to the API through DV360's query sharing.
- **Observed latency (live, 2026-11-05):** the first call in a session took 7.7 s. Afterwards, `queries.list` (page size 1 or 100, ~75 KB for 100) and `queries.get` took 1.1–1.9 s each.
- **Methods used** (`integrations/bidmanager/client.ts`): `queries.create`, `queries.run` (never `synchronous`), `queries.get`, `queries.list` (`pageSize` 1–100, `pageToken`, `orderBy` `queryId`/`metadata.title`, no filter; `queries` absent when empty), `queries.delete` (also deletes the query's reports; empty JSON body), `queries.reports.get`. IDs are JSON strings. **Verified (docs, 2026-11-06).** Since also `queries.reports.list` (`GET /v2/queries/{queryId}/reports`; `pageSize` 1–100, `orderBy` `key.reportId` with an optional ` desc`; `reports` absent when empty), used only by the one-call lookup after an ambiguous `queries.run`. **Verified (docs, 2026-11-12) and live (2026-11-13):** `orderBy=key.reportId desc` is accepted (200) and returns numerically descending IDs, newest first, on our own `[MCP]` query and on a saved query with more than 100 reports. An exact reversal against a complete list of several reports was not shown (no suitable saved query among 22 checked).
- **No creation time** on `Query`, and no documented title length limit; the title becomes the report file name. The server's own queries carry a UTC timestamp in their title (`[MCP] <description> <YYYY-MM-DDTHH:MM:SSZ>`). **Verified (live, 2026-11-06):** top-level keys are `queryId`, `metadata`, `params`, `schedule`.
- **Report states:** `QUEUED`, `RUNNING`, `DONE`, `FAILED`; `finishTime` and `googleCloudStoragePath` appear once finished. **Verified (live, 2026-11-06):** a tiny one-partner report went `QUEUED` → `DONE` in about a minute.
- **Report file link survives query deletion:** the link downloaded without credentials (200) before and after its query was deleted. **Verified (live, 2026-11-06).**
- **Errors (Verified, live, 2026-11-06):** the body is `{ error: { code, message, status } }`. Missing query: `404 NOT_FOUND`, no reasons. **An invalid `pageToken` returns `500 INTERNAL`, not 400**, so it can't be told apart from a transient server error. No 403 has been observed yet; the 403 reasons the server checks follow Google's general conventions. Google's error guide documents 400, 401, 404, 429 (request **or** reporting quota; only the message tells which), 500, and 504.
- **DV360 UI reports are queries (Verified, live, 2026-11-09):** a report saved in DV360's **Instant reporting** builder is returned by `queries.get` with its full `params`. The **Offline reporting** "New" menu offers only Floodlight and Inventory Availability; STANDARD, YOUTUBE, and REACH reports are built in Instant reporting.
- **Field compatibility (Verified, live, 2026-11-09):** `queries.create` rejects unknown codes (`The following metric is not supported: <code>`) and many incompatible sets. The incompatible-set message is generic (`The combination of dimensions, metrics, and filters in your report is invalid.`) and names no field, so a valid YOUTUBE set was taken from a DV360-built report instead of being probed. Advertiser-currency money metrics need the Advertiser Currency dimension (`Advertiser Currency must be included as a dimension.`) in all three types. YOUTUBE and REACH reports must have exactly one partner (`You cannot select more than one Partner to report on.`); STANDARD needs no partner filter. Several IDs of one filter type act as alternatives (verified with advertiser IDs in all three types). The verified catalog is in `src/integrations/bidmanager/fields.ts`; its evidence is in `docs/code/bidmanager-fields.md`.
- **Report CSV layout (Verified, live, 2026-11-09):** a header row (dimensions first, in `groupBys` order, then metrics); data rows; **a totals row** when there are two or more data rows (every dimension cell empty, every metric cell filled), directly before a blank line; then footer lines (`Report Time`, `Date Range`, `Group By`, `Filter by …`). A report with 0 data rows has no totals row. Headers sometimes differ from Google's Report Builder Names (e.g. `Revenue (Adv Currency)`, `YouTube: Revenue eCPV (USD)`).
- **Live latencies (Observed, 2026-11-13, the smoke run and a Claude Code session: 7 requests, all `200`, no retries):** `queries.list` 1.7–1.9 s, `queries.create` 1.9 s, `queries.run` 4.1 s, `queries.reports.get` 1.1 s and once 11.4 s. A tiny one-partner report was already `DONE` at the first status check.
- **Report XLSX layout (Verified, 2026-11-11, two raw Google exports and a live run):** one `Data` sheet with inline strings only (no shared-strings table) and raw numeric values; the same header / data / totals row / empty row / footer sequence as the CSV. In a multi-currency report, the totals row leaves advertiser-currency amounts empty (Google doesn't sum across currencies). The footer has one `Group By:` row per dimension column, a missing-rows warning (when present) before `Report Time:`, an `MRC Accredited Metrics` line, the billing note, and `Filter by … ID:` rows holding `id (name)` lists. CSV and XLSX of the same query give identical headers, rows, totals, and footer lines, except that **CTR is a fraction in XLSX and a percent string in CSV**.
- **Rate formats (Verified, live, 2026-11-11):** CTR, Completion Rate (Video), TrueView: View Rate, and Active View: % Viewable Impressions are **fractions in XLSX** (every value ≤ 1) and **percent strings in CSV** (`9.9%`, values above 1 occur). eCPM is a plain number in both formats.
- **REACH has no totals row (Verified, live, 2026-11-11):** a REACH report grouped by date over 30 days had exactly 30 data rows and no totals row (STANDARD and YOUTUBE reports with two or more rows do have one). Google does not add up unique reach, so there is no total to misread.
- **Saved queries (Verified, live, 2026-11-11):** the test account had 56 (YOUTUBE 28, STANDARD 27, REACH 1), all CSV and one-time, none with notifications or a share list. `queries.run` with a `dataRange` override on a saved query left its range, format, parameters, and title unchanged.
- **Report speed (observed, live, 2026-11-11):** small one-partner reports were `DONE` within 1–20 s of starting, often at the first status check; one of 838 rows (previous month, all partners) after about 10 s; a one-year line-item-level report took about 40–60 s and produced an XLSX over the 3 MiB preview cap.
- **Report link (Verified, live, 2026-11-11):** V2-signed `https://storage.googleapis.com/…` URL with `GoogleAccessId`, `Expires`, and `Signature` parameters. A tampered signature returns `403`.
- **Report size:** one partner, one day, and every STANDARD dimension produced a CSV over 100 MB (more than 151,000 rows). **Observed (live, 2026-11-09).**
- **YOUTUBE entity filters and preset combinations (Verified, live, 2026-11-16 probe; one active YouTube advertiser, 33 reports, all `DONE` in 9–19 s, test queries left for cleanup):**
  - YOUTUBE reports filtered by `FILTER_MEDIA_PLAN`, `FILTER_INSERTION_ORDER`, or `FILTER_LINE_ITEM` (together with the advertiser and partner filters) return only that entity, with views and revenue equal to its row in the unfiltered report grouped by the same level. Impressions matched too, except one run that was 1 impression off (8,290,545 against 8,290,546); a rerun matched exactly. Google's figures drift slightly between runs, so compare to within a few impressions, not exactly.
  - YOUTUBE accepts grouping by campaign, insertion order, and line item in one report (3 levels, 6 dimension columns).
  - A STANDARD `delivery` report filtered to that YouTube line item returned its row (impressions 69 above the YouTube report's, about 0.001%): STANDARD reports do cover YouTube & Partners line items. One sample.
  - Every `get_performance` preset reached `DONE` for each breakdown kind it allows: `delivery` for total, day, week, month, campaign, insertion order, line item, and a campaign target; `video`, `viewability`, `conversions` for total, day, line item; `youtube` for total, campaign, line item; `reach` for total, day, week, month, line item, and a campaign target. Not run live: week and month for `video`, `viewability`, `conversions`; campaign and insertion order children for those three and for `reach`; insertion order and line item targets for every preset.
- **Live check in Claude Code, `get_performance` (Verified, live, 2026-11-17; one campaign and its line items, 15 reports `DONE`):**
  - A campaign named in plain words, with its advertiser named, returned the metadata header and the row in one call: 24.5 s cold (advertiser search over 15 partners included), 10.7–12.7 s with IDs, 15–16 s for a CSV day report and a 365-day line-item report. Reports finished inside the 20 s wait every time, so the pending-ticket path was **not seen live** (covered offline by `request-counts.test.ts`).
  - All six presets ran `DONE` on the campaign (`youtube` on a YouTube & Partners line item); breakdowns checked: total, day (CSV), month (advertiser, 90 days), line item (campaign and advertiser level, 365 days). Totals rows matched across reports for the same advertiser and range.
  - Ambiguous campaign name (11 matches) and ambiguous line item name (two line items with the same name in two insertion orders) started nothing and listed candidates in 1.1–1.6 s. A line item whose flight has not started returned "0 data rows" as a result, not an error.
  - **REACH without a day, week, or month dimension is limited to 93 days.** A 365-day REACH line-item report failed at `queries.create` (not at run) with `invalid_request` and the text "Unless including Date, Week, or Month as a dimension, reach reports can't span more than 93 days"; the same report for 90 days ran `DONE`. No retry, no report started, 2.5 s. The `get_performance` description now says so.
  - Logs: 70 Google requests, all `200`, no retries; no ID, name, link, signature, account, or project value in any line. Cleanup listed queries twice for 8 starts (the 30-minute throttle).
- **Page tokens:** a token still worked 16 minutes after it was issued. **Verified (live, 2026-11-06)**; longer lifetimes are not documented or measured.

## Display & Video 360 API

- **Purpose:** retrieve advertisers, campaigns, insertion orders, and line items (read-only).
- **Version: v4.** Generally available since 2025-03-27, with no deprecation or sunset announced. v5 was released as a **public beta** on 2026-10-22, with no GA date, and is not used. v3 is deprecated (sunset 2025-10-07); v2 and v1 are sunset and return errors. **Verified (docs, 2026-11-04; re-checked 2026-11-12 and 2026-11-13: v5 still beta, v4's deprecation and sunset dates still blank).** Re-check before M7.
- **Sunset methods (Verified, docs):** since 2026-02-23, the campaign and insertion order `assignedTargetingOptions` methods and `lineItems.generateDefault` return `404`.
- **`advertisers.list`:** requires a `partnerId` ("Cross-partner listing is not supported"); returns only advertisers the calling account can access; paginated with `nextPageToken`. **Verified (live)** with one partner.
- **List methods used (Verified, docs, 2026-11-12):** all `GET`, returning arrays of full resources with `nextPageToken`.

  | Method | `pageSize` | Filter fields | Archived excluded by default |
  |---|---|---|---|
  | `partners.list` | 1–200 (default 100) | `entityStatus` | no |
  | `advertisers.list` | 1–200 (default 100) | `advertiserId`, `displayName`, `entityStatus`, `updateTime` | no |
  | `advertisers.campaigns.list` | 1–200 (default 100) | `campaignId`, `displayName`, `entityStatus`, `updateTime` | yes |
  | `advertisers.insertionOrders.list` | **1–100** (default 100) | `campaignId`, `displayName`, `entityStatus`, `updateTime` | yes |
  | `advertisers.lineItems.list` | 1–200 (default 100) | `campaignId`, `displayName`, `entityStatus`, `insertionOrderId`, `lineItemId`, `lineItemType`, `updateTime` | yes |

  Every field uses `=`, except `updateTime`, which uses `>=` or `<=`. `displayName` matching is exact (the guide's substring operator `:` is not listed for these methods, and returns `400` live; see below). Filters are at most 500 characters. `OR` joins restrictions on the same field only; `AND` joins different fields. Each resource also has a `get` method. The `display-video` scope covers them all.
- **Quotas (Verified, docs, 2026-11-12):** 1,500 requests per minute per project; 300 per minute per advertiser per project (advertiser ID in the path); no daily limit stated; increases cannot be requested. Exceeding a quota returns `429 RESOURCE_EXHAUSTED`.
- **First live probe (Verified, live, 2026-11-12, test partner and test advertiser; the probe prints only counts, key names, and enum values):**
  - **Lists work** with the shared account: 15 partners (all `ACTIVE`); more than 200 advertisers under the test partner (a full page of 200 plus a token; `ACTIVE` and `PAUSED` only); `advertisers` and `partners` carry `generalConfig.currencyCode`, and advertisers also carry `generalConfig.timeZone`.
  - **Currency can differ between partner and advertiser:** 3 of 200 advertisers had a currency different from the partner's. So the advertiser lookup for child calls is required.
  - **Default archive exclusion confirmed:** the test advertiser's campaigns went from 9 (default) to 17 (explicit full status list), insertion orders from 17 to 29, line items from 0 to 35. In every case the default list was a subset of the explicit list, and every extra entity was `ARCHIVED`. Both traversals were complete (no page cap reached), but they are two observations in time.
  - **`DRAFT` insertion orders are common:** 15 of the 17 default insertion orders were drafts, so drafts are listed by default. No `SCHEDULED_FOR_DELETION` entity was seen.
  - **List and get parity:** the top-level keys were identical for partners, advertisers, campaigns, and insertion orders; the list and get entities were deep-equal for partners, campaigns, and insertion orders. The advertiser list entry and its `get` differ in some **nested value** (not in any top-level key; not yet investigated). Line items (second run, an advertiser with 16 active line items): top-level keys identical and the entities deep-equal. Insertion orders were deep-equal in the first run; in the second run that one `get` hit the client's 30 s timeout once (every other request took 0.4–3.7 s), so treat a metadata call as able to take the full 30 s.
  - **Sizes:** campaigns about 0.5–0.65 KB of JSON each; insertion orders about 1.5–1.7 KB.
  - **Insertion order shape:** keys include `budget`, `pacing`, `bidStrategy`, `kpi`, `partnerCosts`, and `insertionOrderType`; 16 had `BUDGET_UNIT_CURRENCY` and 1 had `BUDGET_UNIT_IMPRESSIONS`; automation types `NONE` (12) and `BID_BUDGET` (5); at most 1 budget segment; pacing `FLIGHT` (15) and `DAILY` (2), with `dailyMaxMicros` present. Campaigns carry `campaignFlight.plannedSpendAmountMicros` and `campaignGoal`, and none had `campaignBudgets`.
  - **Line item shape (second run, 16 active line items; 29 more archived):** about 1.9 KB of JSON each (1.9–2.5 KB). Top-level keys: `lineItemType`, `budget`, `flight`, `bidStrategy`, `pacing`, `frequencyCap`, `partnerCosts`, `partnerRevenueModel`, `creativeIds`, `targetingExpansion`, `youtubeAndPartnersSettings`, `conversionCounting`, `warningMessages`, plus the IDs. Types seen: `DISPLAY_DEFAULT` (4), `VIDEO_DEFAULT` (1), `YOUTUBE_AND_PARTNERS_REACH` (11). Budget allocation: `FIXED` (12) and `UNLIMITED` (4; no `AUTOMATIC` seen); budget unit `CURRENCY` (15) and `IMPRESSIONS` (1). Flight: `INHERITED` (15; **every one still carries a `dateRange`**) and `CUSTOM` (1). Bid strategy, by the key that is set: `youtubeAndPartnersBid` (11), `maximizeSpendAutoBid` (4), `fixedBid` (1).
  - **Second advertiser's insertion orders:** 25 default (17 `ACTIVE`, 6 `PAUSED`, 2 `DRAFT`) plus 1 archived; at most 3 budget segments; automation `NONE` (9), `BUDGET` (9), `BID_BUDGET` (7); all `FLIGHT` pacing with no daily caps; 1 impression-based insertion order. Its campaigns: 12 default, equal to the explicit list.
  - **Paging (Verified, live):** three consecutive `pageSize=1` line item pages returned distinct IDs. **A page token from one filter was accepted with a different `statuses` filter** (success, no error), so Google does not bind a token to its filter. A caller that changes the filter between pages silently gets inconsistent pages. Token lifetime was not measured.
  - **Errors (status, no `ErrorInfo` reasons in any of them):**
    - an invalid `pageToken` → `400 INVALID_ARGUMENT` (unlike Bid Manager's `500`);
    - **a non-existent partner or advertiser ID → `403 PERMISSION_DENIED`, not `404`** (`advertisers.get` with a bad ID, and `advertisers.list` with a bad `partnerId`);
    - a non-existent line item under a valid advertiser → `404 NOT_FOUND`.
  - **The substring filter is not supported:** `displayName:"…"` on `advertisers.list` → `400 INVALID_ARGUMENT`. The same `400` came back on `lineItems.list`. So names are matched locally by the server (`find_entities`).
  - **Latency:** 0.8–3.7 s per request; the first call took 2.8 s.
- **Advertiser list vs get (Verified, live, 2026-11-12):** the list entry and `get` differ only in `updateTime` (a string value). Nothing else, at any depth, so list rows are as complete as `get`.
- **Impression budget unit (Verified, live and DV360 UI, 2026-11-12):** under `budgetUnit` `BUDGET_UNIT_IMPRESSIONS`, an insertion order segment's `budgetAmountMicros` is a **plain impression count, not micros, despite its name**. The API returned `15800000`, and DV360's UI showed the same insertion order's budget as 15,800,000 impressions. Its impression-based line item (same name) held `maxAmount` `15800000`, which Google documents as a count. The impression unit of a campaign budget is not verified (no campaign budgets exist on the test advertisers).
- **Line item budgets without an amount (Verified, live, 2026-11-12):** all 11 `YOUTUBE_AND_PARTNERS_REACH` line items on the second test advertiser had `budgetAllocationType` `FIXED` and `budgetUnit` `BUDGET_UNIT_CURRENCY` but **no `maxAmount` key**; unlimited line items also omit it. The server shows `budget: no amount on the line item (see its insertion order)` for the first case.
- **live check (Verified, live, 2026-11-12, real server, 27 DV360 requests):** 12 tools listed; list_partners 15 rows with currencies and `End of list.`; list_advertisers pages of 40 with a token, the second page with no repeated ID, and a token reused with different statuses refused as a different request; campaign, insertion order, and line item lists with the advertiser-currency note; complete walks of the line items with and without `ARCHIVED` (16 vs 45 IDs, a strict subset, all 29 extras `ARCHIVED`, no duplicates); `get_metadata` for all five types (0.8–2.9 K characters, details present, an insertion order with a `last` segment); a wrong advertiser ID returned the new `access_denied` text. Calls took 1.1–2.9 s.
- **drill-down (Verified, live, 2026-11-12, Claude Code over the real server):** partners → 273 advertisers under one partner (7 pages of 40, nothing lost) → campaigns → insertion orders → line items → details → a report filtered by the IDs found, with no lookup report. DV360's History showed no changes. One `insertionOrders` call hit the 30 s client timeout and succeeded on retry (the second timeout seen that day).
- **Report filters footer (Observed, live, 2026-11-12):** a report filtered only by advertiser and insertion order listed every partner the account can see under its partner filter lines. Google adds these itself; the numbers were unaffected.
- **Live latencies (Observed, 2026-11-13, the same two runs: 21 requests, all `200`, no retries or timeouts):** list and get calls 0.9–4.6 s (the slowest an `advertisers.list` of 5), `advertisers.get` 1.1–1.9 s.
- **Name lookup, `find_entities` (Observed, live, 2026-11-13; a script client plus Claude Code over the real server; DV360 reads only):**
  - **Cold advertiser search across all partners:** 1 `partners.list` + 16 `advertisers.list` (15 partners, one with 2 pages of 200), 540 advertisers, **19.8 s** in the script and **11.7 s** in Claude Code. That is up to 80% of the 25 s scan budget, so on a slow day some partners can be left unsearched (the result then says so). No partner refused access and none failed, so the denied path is unit-tested only.
  - **Warm (directories cached):** 1 `partners.list` and no `advertisers.list`, 1.2–3.5 s. A search under one cached `partnerId` makes no request at all.
  - **Matching on real names:** partner fragments ranked the intended partner first (5 of 5), and full names in another case were exact matches. Campaign and insertion order names with swapped case matched exactly. Common words gave the expected ambiguous lists (6 and 10 matches). An archived line item is hidden by default and found with `statuses: ARCHIVED`. A short fragment matched 61 advertisers (20 shown plus a "more" line), and the full name found exactly the one.
  - **Turkish letters and accents:** 16 of 200 advertiser names under the test partner contain them. Three were each found exactly (rank 1) by Turkish upper case, default upper case, and swapped case.
  - **Claude Code** resolved advertiser → campaign → details with `find_entities` twice and `get_metadata` once: 3 tool calls, 20 DV360 requests, all `200`.
  - **Logs:** no ID, name, or query in any line (41 script lines; 24 server lines).
- **Not yet verified live:** page-token lifetime, the `403` for an advertiser that exists but isn't accessible, and whether Google sends `Retry-After` on a `429` (none has occurred; nothing was provoked to find out).

## Security

Never document credentials, API keys, access tokens, or other secrets here.
